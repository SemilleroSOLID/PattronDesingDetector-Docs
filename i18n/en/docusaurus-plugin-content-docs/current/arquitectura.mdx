# Architecture

Pattern Detector is **two independent repositories** that communicate only
over HTTP — they share no code, no process, and each can be developed,
tested, and deployed separately. Both are **private** (access restricted to
the research team), so this page doesn't link to them directly:

- **Backend** (Python / FastAPI). Does *all* the Java analysis.
- **Extension** (TypeScript / VS Code). Has no Java parser of its own; it
  captures files and asks the backend to analyze them.

## Where everything lives

**Backend:**

| Folder | What's there |
|---|---|
| `app/api/` | The 3 endpoints (`analyze.py`, `feedback.py`, `health.py`) — receive the request, delegate, decide the HTTP status code |
| `app/services/` | The detectors (one file each: `god_class_detector.py`, `singleton_detector.py`, etc.), the orchestrator (`batch_analysis.py`), the AI clients (`ai_analysis_client.py`, `ai_providers/`) |
| `app/schemas/` | The Pydantic models for the contract (`GodClassWarning`, `SingletonEvidence`, etc.) |
| `app/core/config.py` | All thresholds and settings, via `pydantic-settings` from `.env` |
| `tests/` | The `pytest` suite — one test file per detector, plus integration tests |

**Extension:**

| Folder | What's there |
|---|---|
| `src/extension.ts` | Entry point — registers commands and the auto-capture listener on save |
| `src/services/` | `BackendAnalyzerService` (HTTP to the backend), `scanner.ts` (walks the project), `ProjectSummaryService` (orchestrates a full run), `markdown.ts` (generates the report) |
| `src/providers/` | The UI: findings tree, summary panel webview, conflict panel |
| `src/models/types.ts` | The shared interfaces on the extension side |
| `src/repositories/` | `CodeCaptureRepository` — persists captured content in `.prueba/` |

## Backend: Java is analyzed with two tools

The analysis contract doesn't come from a single parser:

- **tree-sitter** (`java_tree_sitter.py`) produces the structural part —
  `package`, `imports`, `types`, `usedClasses` — and the signals that feed
  the AI suggestions (`extract_method_signatures`).
- **`declaredMethods`** comes from a separate regular-expression engine
  (`java_analyzer.py`).

If you're going to touch how declared methods are extracted from a class,
`java_analyzer.py` is where to look — not `java_tree_sitter.py`.

## Backend: two AI roles, configured separately

`ai_analysis_client.py` resolves **one adapter per role** (not a single
global one):

- **`REFACTOR_PROVIDER`/`REFACTOR_MODEL`** — generates the refactor
  suggestion.
- **`QA_PROVIDER`/`QA_MODEL`** — evaluates it before delivering it
  (QA-Refactor pipeline: if it rejects the suggestion, it sends actionable
  feedback back to the refactor agent and retries, up to a configurable
  maximum of rounds).

The two roles can use different providers (today: NVIDIA and Gemini, via
`app/services/ai_providers/factory.py`) — in practice, the provider that
generates best isn't necessarily the one that evaluates best.

## Multi-antipattern conflict

When the same class triggers **two or more** structural violations at once
(God Class, SRP, DIP, OCP, LSP), the backend doesn't pick which one to
suggest on its own: it asks an AI model
(`priority_recommendation_service.py`) and exposes the recommendation in
the response. The extension shows it to the user, who chooses — and that
choice triggers `POST /analyze/refactor-choice`, which is where the
suggestion for the chosen antipattern actually gets generated.

## Extension: no local analysis

The extension captures files (`ProjectScanner`), calls the backend
(`BackendAnalyzerService`, via Node's native `fetch` — no `axios` or
`node-fetch`) and renders whatever comes back. The only piece that runs
fully locally is `TechStackAnalyzer` (parses `pom.xml`/`build.gradle` for
the report's tech-stack section) — it doesn't touch Java analysis, so it
doesn't need the backend for that.

If the backend is unavailable, the extension **has no local fallback**: it
surfaces `BackendUnavailableError` with the configured URL, and that run
simply produces no new analysis — this is a deliberate decision, not a
pending limitation.

## Error contract and compatibility

Two design rules that aren't visible from reading a single file, but that
matter as soon as you start touching the contract between the two repos:

**Who decides the HTTP status code.** Detectors never decide an HTTP
status code — they raise `ValueError` on invalid input (a negative
threshold, an empty class name), and it's the `app/api/` layer that
translates that into a response. If you're writing a new detector, no
matter how "HTTP-friendly" an error case looks to you: raise `ValueError`
and let the API decide.

**Every new field is optional and additive.** When the backend evolved the
contract for the multi-antipattern conflict (`priorityRecommendation`) and
for the QA pipeline (`verificationStatus`, `appliedPreview`), the rule was
always the same: new field, safe `None`/default, never rename or remove an
existing field, never change the behavior of an endpoint for a request
that already worked. An old extension that doesn't know about a new field
simply ignores it — it never breaks. This is what allows the backend and
the extension to be deployed independently without hand-coordinating
versions (see `docs/retrocompatibilidad.md` in the backend for the
case-by-case detail).
