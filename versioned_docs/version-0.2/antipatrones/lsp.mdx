# LSP (sustitución de Liskov)

Un método `override` no puede sustituir de forma segura al método que
declara en su clase base o interfaz cuando rompe el contrato que esa base
prometía. El análisis es **cross-file**: compara cada override contra la
declaración real de su clase base dentro del mismo batch analizado.

## Dos señales, con prioridad

1. **`immediate_throw`** — el cuerpo del override lanza inmediatamente una
   excepción de "no implementado" (`UnsupportedOperationException`,
   `NotImplementedException` por default, configurable). Tiene prioridad:
   si se cumple, ni se evalúa el tipo de retorno.
2. **`incompatible_return_type`** — el tipo de retorno del override es
   distinto al de la base, y esa relación **no se puede verificar** como
   covarianza válida dentro del batch analizado.

## Por qué "no verificable" y no "inválida"

Java permite que un override devuelva un subtipo del retorno de la base
(covarianza), y eso es perfectamente válido. El detector sigue la cadena de
herencia disponible en el batch para confirmarlo — pero si el tipo de
retorno (de la base o del override) no está declarado en el mismo batch
(por ejemplo, es un tipo del JDK como `Collection`/`List`), no hay forma de
verificar la relación. En ese caso se prefiere marcar como sospechoso antes
que dejarlo pasar en silencio: un `List<String>` sobre una base que declara
`Collection<String>` se marca si ninguno de los dos tipos está en el batch.

Dos casos que **no** se marcan aunque a primera vista parezcan sospechosos:

- El retorno de la base es uno de sus propios **parámetros de tipo
  genérico** (`T` en `interface Repo<T> { T find(int id); }`) — cualquier
  tipo concreto en el override es válido ahí.
- La base tiene **overloads ambiguos** (mismo nombre y aridad, distinto
  retorno) — no se puede determinar con certeza cuál contrato se
  sobreescribe, así que no se marca por tipo de retorno (el chequeo de
  `immediate_throw` sigue aplicando igual).

## Deduplicación en jerarquías diamante

Si una clase hereda el mismo método (mismo nombre + misma aridad) de más de
una base a la vez (`extends` + `implements`), eso genera un candidato por
cada base — pero es un solo override real, así que se deduplica por
`(clase, firma)` para producir **una** advertencia, no varias.

## Sin sugerencia de IA

Igual que DIP y OCP, LSP no genera una sugerencia de refactor por IA.
